# INCR: Incremental Compilation

## Intent

This package specifies the generic build-record, currentness, incremental-planning, update-contract, protected-scope, and lineage mechanics used by incremental compiler runs.
Phase-specific update semantics remain owned by pipeline definitions under [DR-003](../decisions/003-slc-phase-execution.md).

Essential project-specific reference: `slc`, this project's compiler CLI.

## Build record

### INCR-7

Where an invocation is a full or full-link run with canonical output or `-o`, when it succeeds after executing at least one scheduled step or accepting an explicit adoption, the slc command shall, for canonical output other than the reserved `slc` meta-pipeline, derive the result-independent canonical plan before changing the artifact directory, use stable kind/ordinal step identities while selecting pins by authored phase/pass basename or reserved `link` and assigning no pin key to the SLC-owned built-in normalizer, use explicit host-supplied interpreted and compiled executor, deterministic-generator/checker, compatibility, and package descriptors rather than inspecting function objects, derive a selected compiled executor from that host configuration plus the current pin's complete execution identity and runtime profile, record `inputClosure: "closed"` only for a root definition with an explicit `## Pin Inputs` section while retaining explicit request references as semantic inputs, write regular non-symbolic-link files `<art-dir>/.slc-build.json` and `<art-dir>/.slc-source`, encode the record as canonical compact UTF-8 JSON in contract field order followed by one LF, make every field, literal value, nullability, hash, canonical artifact-directory-relative POSIX path, ordering, uniqueness, cross-reference, plan-identity projection, product inventory, provenance, generation, origin, optional trace, and adoption transition satisfy [DR-021's exact `sublang.slc.build.v1` contract](../decisions/021-incremental-build-records-scoped-updates.md#sublangslcbuildv1), make the raw snapshot bytes hash-equal to both source identities, and shall for `-o` or the reserved meta-pipeline retain non-lineage execution, request no host build identity, and write neither lineage file ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#build-lineage), [DR-007](../decisions/007-slc-phase-artifact-pinning.md#hashing-and-portability)).
Where an invocation is a single-phase, standalone-pass, or direct-link form, when it runs, the slc command shall retain its existing execution path and specified output placement, request no host build identity, and neither create nor advance a build record or source snapshot ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#exact-reuse-and-conflicts)).

## Currentness and planning

### INCR-9

Where either reserved lineage-metadata path or a pending sealed promotion stage beside the artifact directory is present, when the slc command plans a full or full-link run, the slc command shall finish forward-only promotion recovery, identify the current canonical plan and validate every applicable pin, and only then classify lineage and structured recovery choices without writing the bundle; a stale or malformed pin shall fail under [PHEXEC-27](phase-execution.md#phexec-27) with its pin diagnostic and explicit compiled-artifact build-and-review guidance before lineage classification or recovery choices are considered; after valid pins it shall treat an orphaned record or snapshot, malformed or noncanonically encoded JSON, a missing, unknown, null, or wrong-typed field at any schema depth, an unsupported schema or hash algorithm, an invalid hash, locator, managed path, order, duplicate ID or path, unresolved or inconsistent cross-reference, link-kind/null combination, source/snapshot identity, product/step relation, generation, origin, compatibility gate, or adoption transition, either metadata path being a symbolic link or wrong file type, or an inventory path not derivable from the recorded canonical plan as a conflict; otherwise it shall verify the source snapshot and every recorded input and managed output by exact bytes, treat a lineage as adopted for automatic currentness only when every scheduled step has `origin: "user-adopted"` and `trace: null`, compare plan-topology compatibility only by ordered scheduled-step kind, source and target formats, and canonical semantic-product target paths while excluding step names, plan inputs, input-closure declarations, invocation options, result-independent identities, and deterministic products from that compatibility projection, classify an unexpected snapshot or an automatic-mode managed-output mismatch as a conflict while passing safe `--adopt` product mismatches to [INCR-34](#incr-34), classify changed source bytes, changed build-plan inputs, or plan-topology drift in a non-adopted lineage whose recorded managed outputs remain exact as rebuild inputs rather than current state while passing an unchanged-source `--adopt` request with compatible plan topology and valid current pins to [INCR-34](#incr-34), classify the same drift in an adopted lineage as a conflict, classify plan-topology drift in an adopted lineage or accompanied by managed-output drift as incompatible with only `--rebuild` recovery, make a phase with no closed content-identified declaration of its output-affecting readable inputs ineligible for phase-result reuse or update except for exact whole-lineage reuse accepted under [INCR-34](#incr-34), and diagnose an automatic conflict with both `--adopt` and `--rebuild` only for a lineage satisfying [INCR-34](#incr-34)'s preconditions other than the flag, otherwise with `--rebuild` alone ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#exact-reuse-and-conflicts), [PHEXEC-27](phase-execution.md#phexec-27), [DR-007](../decisions/007-slc-phase-artifact-pinning.md#semantic-input-closure)).

### INCR-10

Where a recorded pipeline step's current input key, definition/executor identity, semantic options, and target bytes match its record, when the slc command walks the ordered build plan, the slc command shall reuse that step only after any applicable pin has passed [DR-007](../decisions/007-slc-phase-artifact-pinning.md#currency-and-selection)'s validation and selected the recorded executor; after executing a dirty step, it shall compute downstream currentness from the candidate's actual output hash so byte-identical regeneration does not invalidate an otherwise-current downstream step ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#exact-reuse-and-conflicts)).

### INCR-11

Where a non-adopted lineage's every applicable pin has passed validation and a dirty pipeline step either has no complete update contract and validated trace or has definition, executor, declared-semantic-input, link-target, compatibility, or semantic-option drift that remains valid for ordinary execution, when the slc command plans that step, the slc command shall select its ordinary execution without asking an agent to classify the change ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#deterministic-update-planning), [DR-003](../decisions/003-slc-phase-execution.md#generic-vs-phase-specific)).

## Update contracts and execution

### INCR-12

Where a phase definition contains a `## Update` section, the definition shall opt into scoped update only when the section begins with the exact schema declaration and contains the six nonempty semantic subsections exactly once and in the order required by [DR-021's `## Update` grammar](../decisions/021-incremental-build-records-scoped-updates.md#update-grammar); the slc command shall validate that structure without interpreting its phase-owned stable-unit, target-scope, dependency, structural/global, instruction, or semantic-verification prose, treat a missing or malformed contract as ordinary-execution-only, and contain no format-specific update rule, change-ratio threshold, or generation threshold ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#deterministic-update-planning), [DR-003](../decisions/003-slc-phase-execution.md#generic-vs-phase-specific)).

### INCR-13

Where [PHEXEC-39](phase-execution.md#phexec-39) makes optional `sublang.slc.update.v1` metadata available from an ordinary or update execution, when the slc command evaluates that metadata, the slc command shall accept at most one value and require the exact schema, hashes, byte lengths, complete ordered adjacent partitions, opaque scope strings, classifications, and ordered complete dependency closures defined by [DR-021's trace schema](../decisions/021-incremental-build-records-scoped-updates.md#sublangslcupdatev1); bind an ordinary trace's input to the step's sole compile operand and its target to the semantic product; record valid ordinary metadata inline; record `trace: null` and disable later update when ordinary execution supplies no valid metadata; and reject an update candidate that omits, malforms, or misbinds its replacement metadata ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#trace-contract), [PHEXEC-3](phase-execution.md#phexec-3)).

### INCR-14

Where a prior accepted trace is available for a dirty step, when the slc command determines scoped-update eligibility, the slc command shall compute a provisional dirty-unit and target dependency closure without an agent call, select ordinary execution for a mechanically evident unmapped or ambiguous span, changed recorded structural or global scope, cross-unit edit, broken ordering, or incomplete trace, and otherwise let the update candidate's replacement trace prove that eligible input-unit structure, classifications, and dependency closure remain within the provisional boundary ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#deterministic-update-planning)).

### INCR-15

Where a dirty phase is eligible for scoped update, when the slc command executes its update contract, the slc command shall add the exact `sublang.slc.update-request.v1` object to the compile request, bind its `source`, `prior-input`, and `prior-target` reads plus the one candidate sink through `sublang.slc.workspace.v1`, embed the accepted step's field-for-field recorded prior trace, provide the canonical ordered byte-diff hunks, and make the allowed target scopes equal the prior-target-ordered union of the dirty local input scopes' recorded complete closures as defined by [DR-021](../decisions/021-incremental-build-records-scoped-updates.md#update-request); require a complete candidate target and out-of-band replacement trace bound to the current input and candidate bytes; stage the candidate; and reject it unless the replacement trace preserves the eligible input-unit structure and classifications without expanding the allowed dependency closure, every unchanged input scope retains its exact dependency closure, every dirty input closure stays within the allowed target scopes, every target scope outside the allowed closure keeps the same scope string, order, classification, and exact bytes, every added, removed, or changed target scope lies inside that closure, every protected input remains unchanged, the trace is structurally valid, and the ordinary generic and definition-owned semantic checks pass ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#scoped-execution-and-acceptance), [PHEXEC-5](phase-execution.md#phexec-5), [PHEXEC-6](phase-execution.md#phexec-6)).

### INCR-16

Where a scoped-update execution honors its physical workspace binding, when that execution or its required downstream verification is blocked or rejected, the slc command shall discard the complete staged run, write no candidate byte to the canonical bundle, source snapshot, or build record, recommend `--rebuild`, and make no automatic ordinary-phase invocation, so one failed update does not become a hidden second agent call; a detected out-of-binding write shall fail without promotion but is outside this rollback guarantee ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#scoped-execution-and-acceptance), [PHEXEC-6](phase-execution.md#phexec-6), [PHEXEC-12](phase-execution.md#phexec-12)).

### INCR-17

Where an accepted step changes its output bytes, when the slc command continues the build, the slc command shall replan every downstream step from the changed bytes, execute every dirty link in full because link phases are not scoped-update-capable in this schema version, regenerate deterministic entry and verification products whose inputs changed, run the complete applicable emitted verification suite, and record the new lineage only after all required checks succeed ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#scoped-execution-and-acceptance), [DR-009](../decisions/009-slc-playbook-pipeline-compilation.md#verification-is-deterministic-and-artifact-derived)).

## Playbook trace and explicit rebuild

### INCR-18

Where a full or full-link `playbook` run receives generic update traces from the SLC-owned normalization definition or Playbook-owned phase definitions, when the slc command records or evaluates those traces, the slc command shall validate only their opaque scopes, ranges, identities, classifications, and complete closure cross-references without hard-coding normalized-step, GEARS-item, or FSM-state meanings and shall select ordinary execution when any contract-required closure member or declared structural scope is absent or inconsistent ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#playbook-traceability), [DR-003](../decisions/003-slc-phase-execution.md#generic-vs-phase-specific)).

### INCR-19

Where an invocation carries `--rebuild`, when the slc command validates its form, the slc command shall accept only a canonical full or full-link invocation without `-o` or `--adopt` — bypassing build-record reuse and scoped-update planning, permitting explicit replacement or source rebinding, and executing the complete ordinary plan; for a lineage-eligible pipeline it shall replace the snapshot and record entries themselves only after success without following their symbolic links or trusting an invalid prior inventory for deletion, advance a schema-valid same-source lineage's generation or refuse before executor work when that would exceed the maximum safe integer, and start an explicit source rebound, or a rebuild whose prior reserved pair is untrusted, at generation `1`, while for the reserved `slc` meta-pipeline it shall write no lineage metadata — and shall refuse every other form ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#exact-reuse-and-conflicts)).

## Explicit adoption

### INCR-34

Where an invocation carries `--adopt`, when the slc command validates its form and current lineage, the slc command shall accept only a canonical non-`slc` full or full-link invocation without `-o` or `--rebuild` whose schema-valid record and snapshot retain the same source locator and exact source bytes, whose current applicable pins validate, whose managed paths and complete semantic-product inventory are safe, and whose recorded and current canonical plans have the same ordered semantic-product roles, formats, and target paths; it shall derive the current definition, selected-executor, declared-semantic-input, link-target, deterministic entry/verification generator and checker, compatibility, and semantic-option identities rather than requiring those identities to match the record, reject every other form and every malformed, orphaned, source-drifted, topology-drifted, missing-semantic-product, wrong-typed, unsafe, or symbolic-link managed-path case rather than treating adoption as cold-build repair or source rebinding, pass a safe missing or changed deterministic derivative to [INCR-35](#incr-35)'s trusted regeneration, and fail an invalid current pin under [PHEXEC-27](phase-execution.md#phexec-27) with its pin diagnostic and explicit compiled-artifact build-and-review guidance before either lineage recovery option is evaluated ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#explicit-adoption), [PHEXEC-27](phase-execution.md#phexec-27)).

### INCR-35

Where [INCR-34](#incr-34) accepts an adoption candidate, when the slc command evaluates the current products, the slc command shall treat explicit user attestation — not regenerated verification — as semantic authority for the complete set of scheduled normalization, phase, pass, and link products; invoke no semantic executor; hash and record all of them with `origin: "user-adopted"`, the derived current `plan.identity`, and `lineage.transition: { from, to }` exactly when the prior and current plan identities differ, with `from` equal to the prior identity and `to` equal to the current identity, otherwise `lineage.transition: null`; clear every update trace; regenerate the entry and verification products from trusted current generators in staged state; apply generic and load-integrity checks and the complete applicable regenerated verification suite; and only after success promote the deterministic derivatives and record while leaving the semantic products and source snapshot byte-identical and reporting the adopted products; failure of binding-compliant host work shall write no candidate byte to a canonical path, a generic, load-integrity, or verification failure attributable to inconsistent semantic products shall advise repairing those products before retrying `--adopt` or using `--rebuild`, and every other failure shall report its actual cause and applicable recovery; a later exact invocation shall reuse the whole adopted lineage without requiring closed phase-input declarations; and later drift shall conflict until an eligible unchanged-source refinement or compatible build-identity rebaseline is adopted, or `--rebuild` replaces the lineage ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#explicit-adoption), [VERIFY-18](verification.md#verify-18)).

### INCR-39

Where scoped update is withheld from a release, when the slc command plans any step or receives any phase execution request, the slc command shall select ordinary execution for every step regardless of contract, trace, or eligibility, shall refuse an execution request that carries an update object rather than dropping it or executing ordinarily, and shall keep recording valid ordinary traces so a later release can update from them; while this holds it supersedes the scoped selection, request, and acceptance duties of [INCR-3](../user/incremental-compilation.md#incr-3), [INCR-14](#incr-14), [INCR-15](#incr-15), and [INCR-16](#incr-16), which resume unchanged when the withholding is lifted ([DR-021](../decisions/021-incremental-build-records-scoped-updates.md#scoped-execution-and-acceptance)).
